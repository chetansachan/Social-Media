# System Design: Notification Service

## 1. Executive Summary & Purpose

The **Notification Service** is the central nervous system for user engagement, activity awareness, and real-time alerts in the **SocialFlow** platform. Whenever significant domain events take place—such as a user gaining a new follower, receiving a like or comment on a post, being tagged or mentioned, or receiving critical account security notices—the Notification Service is responsible for capturing, processing, aggregating, persisting, and delivering those notifications across multiple channels.

In a modern social media microservices ecosystem, notifications are far more than a simple database write. A robust Notification Service must solve critical distributed system challenges:
* **Multi-Channel Dispatching**: Coordinating delivery across In-App Real-time (WebSockets / Server-Sent Events), Mobile Push (Apple APNs / Google FCM), and Email (Transactional alerts and digests).
* **High-Throughput Ingestion & Decoupling**: Processing millions of domain events asynchronously without slowing down primary write paths (`post-service`, `follow-service`, `user-service`).
* **Smart Aggregation & Roll-up**: Preventing notification spam when a post goes viral (collapsing "User A, User B, and 45 others liked your post" into a single coherent notification).
* **Ultra-Low Latency In-App Alerts**: Delivering notifications to active, connected users in < 200 milliseconds.
* **Granular Preference Management**: Respecting recipient muting rules, quiet hours, channel opt-outs, and anti-spam rate limits.
* **Fault-Tolerant & Idempotent**: Guaranteeing that transient downstream failures (e.g. mobile push provider timeouts) do not drop messages, and network retries do not produce duplicate alerts.

## 2. Requirements & Design Targets

### 2.1 Functional Requirements

1. **Multi-Event Ingestion**:
   * Asynchronously consume events emitted by other services:
     * `UserFollowed` (from `follow-service`)
     * `PostLiked`, `PostCommented`, `CommentReplied` (from `post-service`)
     * `UserMentioned` (from `post-service` / comment workflows)
     * `PostCreatedBySubscribedCreator` (notification bell / VIP follow from `feed-service`/`follow-service`)
     * `SecurityAlert`, `WelcomeMessage` (from `user-service`)
2. **Notification Inbox (In-App)**:
   * Users can view a paginated list of their notifications sorted reverse-chronologically.
   * Notifications maintain read/unread state (`is_read`, `read_at`).
   * Filter notifications by category (All, Mentions, Likes, Follows).
3. **Unread Badge Counter**:
   * Instant retrieval and real-time updating of unread counts (e.g. the bell icon badge "5").
   * Atomic mark-as-read (single item, batch of IDs, or "Mark All as Read").
4. **Real-Time Push to Active Clients**:
   * Connected clients (Web, iOS, Android) receive incoming alerts instantly over persistent WebSocket connections without manual polling.
5. **Smart Aggregation & Deduplication**:
   * Group repetitive events within a time window (e.g., likes from multiple users on the same post).
   * Suppress duplicate events generated by network retries.
   * Suppress self-actions (a user liking or commenting on their own post must never notify themselves).
6. **User Preferences & Policies**:
   * Enable/disable notifications per category (e.g. mute likes, keep mentions).
   * Enable/disable channels per category (e.g. In-App: ON, Push: ON, Email: OFF).
   * Quiet Hours (e.g. suppress push notifications between 22:00 and 07:00 in user's local timezone).
7. **Device Token Management**:
   * Register, refresh, and revoke FCM / APNs device tokens across multiple user devices (phone, tablet).

---

### 2.2 Non-Functional Requirements

1. **Latency**:
   * In-App Real-time Delivery (WebSocket): **p95 < 200ms**, **p99 < 500ms** from event publication.
   * Inbox Query Latency (`GetNotifications`): **p95 < 30ms**, **p99 < 80ms**.
   * Unread Count Query (`GetUnreadCount`): **p99 < 5ms** (served directly from in-memory cache).
2. **Throughput & Scalability**:
   * Support write spikes during peak platform hours (e.g., 50,000+ events/sec).
   * Support horizontal scaling of WebSocket gateway servers to maintain hundreds of thousands of simultaneous idle persistent connections.
3. **Reliability & Delivery Guarantees**:
   * **At-least-once delivery** from the message queue.
   * **Idempotent processing** so retries do not generate phantom notifications.
   * Isolation between channels: a failure in external push notifications (FCM/APNs) must never prevent an in-app notification from being written and delivered via WebSockets.
4. **Data Retention & Lifecycle**:
   * In-app notifications stored in persistent storage for 90 days.
   * Automatic background partitioning and archiving/pruning for stale records.

---

### 2.3 Capacity Estimation (Scale Planning)

* **Daily Active Users (DAU)**: 5 Million
* **Average Events Generated**: Each active user performs ~10 interactions/day that trigger potential notifications $\rightarrow$ **50 Million incoming events/day**.
* **Average Write QPS**:
  $$\text{Average QPS} = \frac{50,000,000}{86,400} \approx 580 \text{ events/sec}$$
  $$\text{Peak QPS (5x factor)} \approx 3,000 \text{ events/sec}$$
* **Read QPS (Inbox & Unread count)**:
  * Users check notifications ~5 times/day $\rightarrow$ $25\text{ Million reads/day} \approx 300\text{ QPS}$ average, $1,500\text{ QPS}$ peak.
  * Real-time WebSocket connections: ~500,000 peak concurrent connections.
* **Storage Estimation**:
  * Each notification record $\approx 500 \text{ bytes}$ (actor ID, target ID, metadata JSON, timestamps).
  * After aggregation, ~35 Million persisted notifications/day $\approx 17.5 \text{ GB/day}$.
  * 90-day retention $\approx 1.57 \text{ TB}$ of storage (readily manageable with PostgreSQL table partitioning or MongoDB).

## 4. Internal Components of the Notification Service

To maintain clean separation of concerns, high throughput, and independent scalability, the Notification Service is composed of six distinct internal layers:

### 4.1 Ingestion & Consumer Engine (`internal/events`)
* Subscribes to domain event streams via Redis Streams consumer groups (`XReadGroup`).
* Reads streams concurrently:
  * `events:follow` (`UserFollowedEvent`)
  * `events:post` (`PostLikedEvent`, `PostCommentedEvent`, `PostCreatedEvent`)
  * `events:user` (`UserStatusChangedEvent`)
* Manages stream offsets, acknowledges processed events (`XAck`), and monitors pending message entries (`XAutoClaim`) to prevent lost messages during service reboots.

### 4.2 Filtering & Self-Action Suppression
* **Self-Action Filter**: Immediately drops events where `actor_id == recipient_id` (e.g. creator liking their own post or commenting on their own thread).
* **Block List Validation**: Queries cache or `follow-service` to confirm that the recipient has not blocked the actor. Blocked actors' interactions are silently discarded.

### 4.3 Aggregation & Deduplication Engine (`internal/services/aggregator.go`)
* **Deduplication**: Computes an idempotency hash for each event:
  $$\text{Key} = \text{dedup}:\{\text{actor\_id}\}:\{\text{verb}\}:\{\text{entity\_id}\}$$
  Uses Redis `SET key 1 EX 60 NX` to eliminate duplicate deliveries within a 60-second window.
* **Smart Roll-Up**: For high-frequency social events (likes, reactions), collapses individual events on the same target entity within a tumbling/sliding window (e.g. 10 minutes):
  * First like: Creates notification "Alice liked your post".
  * Second like within window: Updates notification to "Alice and Bob liked your post".
  * Tenth like within window: Updates notification to "Alice, Bob, and 8 others liked your post".

### 4.4 User Preference & Policy Engine (`internal/services/policy.go`)
* Evaluates whether a notification should be delivered, and through which channels:
  1. **Category Toggle**: Has the user muted `post_likes` or `new_followers`?
  2. **Channel Toggles**: Is `push_enabled` true? Is `email_enabled` true?
  3. **Quiet Hours**: Compares current UTC time against the user's localized quiet hours window (e.g., 22:00 to 08:00). If active, suppresses push/email or defers them.
  4. **Frequency Throttles**: Limits promotional or low-priority push alerts to at most 1 per hour per recipient.

### 4.5 Persistence & Cache Engine (`internal/repository`)
* **PostgreSQL (System of Record)**:
  * Stores complete notification history, actor references, target entity URIs, JSON metadata, and read status.
  * Partitioned by creation month to maintain high index efficiency over time.
* **Redis (Hot Cache & Real-Time Sync)**:
  * Holds atomic unread badge counters: `unread_count:<user_id>`.
  * Increment on new notification (`INCR`); decrement on read (`DECRBY`); reset on mark-all (`SET 0`).
  * Caches user notification preferences to avoid round-tripping to PostgreSQL on every incoming event.

### 4.6 Channel Dispatcher Pipeline (`internal/dispatchers`)
* **In-App Realtime Dispatcher**: Publishes payload to Redis Pub/Sub channel `notify:<recipient_id>`. Connected WebSocket instances pick this up and push the JSON frame down the open TCP socket.
* **Mobile Push Dispatcher (FCM / APNs)**: Asynchronous worker pool that formats payloads with platform-specific badges and sounds, retrieves device tokens from PostgreSQL, and posts to Apple APNs / Firebase Cloud Messaging.
* **Email Dispatcher**: Batches digest emails or sends high-priority transactional emails (security alerts, new login notifications) via SendGrid or AWS SES.

## 5. End-to-End Workflows

### 5.1 Workflow: Social Interaction to In-App Real-Time Delivery

```
[User A: Actor]                [Post Service]                [Redis Streams]         [Notification Service]         [Redis Pub/Sub]         [WebSocket Gateway]         [User B: Recipient]
       │                              │                              │                          │                           │                        │                       │
       ├─── 1. Likes Post ───────────▶│                              │                          │                           │                        │                       │
       │                              ├─── 2. Write Like to DB       │                          │                           │                        │                       │
       │                              ├─── 3. XADD(PostLikedEvent) ─▶│                          │                           │                        │                       │
       │                              │                              │                          │                           │                        │                       │
       │                              │                              ├─── 4. XReadGroup ───────▶│                           │                        │                       │
       │                              │                              │                          ├─── 5. Self-Action Check?  │                        │                       │
       │                              │                              │                          ├─── 6. Preference Check?   │                        │                       │
       │                              │                              │                          ├─── 7. Check Aggregation   │                        │                       │
       │                              │                              │                          ├─── 8. Write to Postgres   │                        │                       │
       │                              │                              │                          ├─── 9. INCR unread count   │                        │                       │
       │                              │                              │                          ├─── 10. PUBLISH ──────────▶│                        │                       │
       │                              │                              │                          │    channel: notify:userB  │                        │                       │
       │                              │                              │                          │                           ├─── 11. Distribute ────▶│                       │
       │                              │                              │                          │                           │                        ├─── 12. WS Push Frame ─▶ Pop-up Alert
       │                              │                              │                          │                           │                        │    & Badge: "3"       │
       │                              │                              │                          ├─── 13. XAck Message ─────▶│                        │                       │
```

#### Step-by-Step Execution:
1. **Event Publication**: User A likes User B's post. `post-service` handles the database write and appends a `PostLikedEvent` to Redis Stream `events:post`.
2. **Event Consumption**: `notification-service` consumer group worker reads the event.
3. **Safety & Policy Check**:
   * Ensures `actor_id (User A) != recipient_id (User B)`.
   * Checks User B's notification settings from Redis cache (confirms `likes` notifications are enabled).
4. **Aggregation & Persistence**:
   * Inspects Redis for an active aggregation window on `target_id` (the post).
   * Persists the notification record to PostgreSQL.
   * Atomically increments User B's unread badge count in Redis (`INCR unread_count:userB`).
5. **Real-Time Distribution**:
   * Publishes message to Redis Pub/Sub topic `channel:notify:userB`.
   * The WebSocket gateway instance holding User B's connection receives the pub/sub event.
   * The gateway sends a lightweight JSON frame down User B's active WebSocket connection.
6. **Acknowledgement**:
   * The consumer acknowledges the message offset in Redis Streams (`XAck`).

### 5.2 Workflow: Aggregation / Roll-Up ("The Like Storm")

When a post is featured or an author has a high follower count, dozens of likes occur per second. Emitting individual notifications would flood the user's inbox and crash their mobile device with push notifications.

```
Incoming Likes on Post #101:
Time 00:00:01 ──▶ Alice likes Post #101 ────▶ [NEW] "Alice liked your post" ──────────────────────▶ Insert DB & Send Push
Time 00:00:05 ──▶ Bob likes Post #101   ────▶ [AGGREGATE] "Alice and Bob liked your post" ─────────▶ Update DB (In-App Only)
Time 00:01:20 ──▶ Carol likes Post #101 ────▶ [AGGREGATE] "Alice, Bob, and 1 other liked your post"─▶ Update DB (Suppress Push)
Time 00:05:00 ──▶ Dave likes Post #101  ────▶ [AGGREGATE] "Alice, Bob, and 2 others liked your post"▶ Update DB (Suppress Push)
```

#### Technical Mechanism:
* An aggregation key is formed in Redis: `agg:{recipient_id}:{verb}:{entity_id}` with a 15-minute TTL.
* **On Event 1**: Key does not exist. A notification row is created in PostgreSQL with `actor_ids = [Alice]`, `total_count = 1`. Key is created in Redis with `notification_id`. A real-time notification is dispatched.
* **On Event 2..N**: Key exists.
  1. Append `actor_id` to the recent actors array (capped at 3 latest names).
  2. Increment `total_count`.
  3. Execute an atomic SQL update:
     ```sql
     UPDATE notifications
     SET actors = $1, total_count = total_count + 1, updated_at = NOW(), is_read = FALSE
     WHERE id = $2;
     ```
  4. Real-time WebSocket updates are throttled (at most once every 30 seconds per aggregated entity). Mobile push notifications are silenced to prevent device alert fatigue.

## 6. Storage & Data Modeling Strategy

### 6.1 Relational Database Schema (PostgreSQL)

PostgreSQL serves as the durable system of record for notification history.

```sql
-- 1. Notification Categories & Types
CREATE TYPE notification_type AS ENUM (
    'follow',
    'post_like',
    'comment',
    'comment_reply',
    'mention',
    'creator_post',
    'system_alert'
);

-- 2. Core Notifications Table
CREATE TABLE notifications (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    recipient_id UUID NOT NULL,
    type notification_type NOT NULL,
    
    -- Target entity being acted upon (e.g. Post ID, Comment ID)
    entity_id VARCHAR(64) NOT NULL,
    entity_type VARCHAR(32) NOT NULL, -- 'post', 'comment', 'user'
    
    -- Actor references: array of user IDs involved in the notification
    actor_ids UUID[] NOT NULL,
    total_actors_count INT NOT NULL DEFAULT 1,
    
    -- Pre-rendered preview text & deep-link navigation URI
    title VARCHAR(120) NOT NULL,
    content_preview VARCHAR(255),
    action_url VARCHAR(512) NOT NULL, -- e.g. "socialflow://posts/e2c04...#comment-9"
    
    -- Status & Timestamps
    is_read BOOLEAN NOT NULL DEFAULT FALSE,
    read_at TIMESTAMPTZ NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Partition Table Example (Monthly)
CREATE TABLE notifications_2026_11 PARTITION OF notifications
    FOR VALUES FROM ('2026-11-01 00:00:00+00') TO ('2026-12-01 00:00:00+00');

-- Indexes optimized for user inbox fetching and unread filtering
CREATE INDEX idx_notifications_recipient_created 
    ON notifications (recipient_id, created_at DESC);

CREATE INDEX idx_notifications_recipient_unread 
    ON notifications (recipient_id) WHERE is_read = FALSE;

CREATE INDEX idx_notifications_entity_aggregation 
    ON notifications (recipient_id, entity_id, type) WHERE is_read = FALSE;

-- 3. User Notification Preferences Table
CREATE TABLE user_notification_settings (
    user_id UUID PRIMARY KEY,
    
    -- In-App preferences
    inapp_likes BOOLEAN NOT NULL DEFAULT TRUE,
    inapp_comments BOOLEAN NOT NULL DEFAULT TRUE,
    inapp_follows BOOLEAN NOT NULL DEFAULT TRUE,
    inapp_mentions BOOLEAN NOT NULL DEFAULT TRUE,
    
    -- Push notification preferences
    push_enabled BOOLEAN NOT NULL DEFAULT TRUE,
    push_likes BOOLEAN NOT NULL DEFAULT FALSE, -- Default disabled to reduce battery/alert fatigue
    push_comments BOOLEAN NOT NULL DEFAULT TRUE,
    push_follows BOOLEAN NOT NULL DEFAULT TRUE,
    push_mentions BOOLEAN NOT NULL DEFAULT TRUE,
    
    -- Email preferences
    email_enabled BOOLEAN NOT NULL DEFAULT TRUE,
    email_weekly_digest BOOLEAN NOT NULL DEFAULT TRUE,
    email_security_alerts BOOLEAN NOT NULL DEFAULT TRUE,
    
    -- Quiet Hours Configuration (in user's local timezone)
    quiet_hours_enabled BOOLEAN NOT NULL DEFAULT FALSE,
    quiet_hours_start TIME NULL, -- e.g. '22:00:00'
    quiet_hours_end TIME NULL,   -- e.g. '07:00:00'
    timezone VARCHAR(64) NOT NULL DEFAULT 'UTC',
    
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 4. Device Tokens Table (for APNs / FCM Push)
CREATE TABLE user_device_tokens (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL,
    token VARCHAR(512) NOT NULL UNIQUE,
    platform VARCHAR(16) NOT NULL, -- 'ios', 'android', 'web'
    device_name VARCHAR(128),
    app_version VARCHAR(32),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    last_seen_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_device_tokens_user ON user_device_tokens (user_id) WHERE is_active = TRUE;
```

### 6.2 Redis Cache Design & Key Structures

Redis provides sub-millisecond badge counts, deduplication guards, and cross-node communication:

| Key Format | Type | TTL | Purpose |
| :--- | :--- | :--- | :--- |
| `unread:{user_id}` | `String` (Integer) | 7 Days | Fast atomic badge counter. Updated on insert (`INCR`), read (`GET`), read mark (`DECRBY`). |
| `dedup:{actor_id}:{type}:{entity_id}` | `String` | 60 Seconds | Atomic idempotency lock (`SET NX EX`) to reject duplicate event deliveries. |
| `agg:{user_id}:{type}:{entity_id}` | `String` (UUID) | 15 Minutes | Tracks the active unread notification ID for rolling aggregation. |
| `prefs:{user_id}` | `Hash` or `JSON` | 24 Hours | Caches user preferences and quiet hours for zero-DB-hit policy checks. |
| `notify:{user_id}` | `Pub/Sub Channel` | N/A | Inter-node message bus distributing real-time alerts to the WebSocket node hosting `user_id`. |

## 7. Real-Time WebSocket Gateway Architecture

Delivering real-time alerts to hundreds of thousands of concurrent client connections requires a distributed, stateless gateway layer backed by Redis Pub/Sub.

```
                    ┌──────────────────────────────────────────────┐
                    │               Client Devices                 │
                    │       (Web Browser, iPhone, Android)         │
                    └──────────────┬────────────────┬──────────────┘
                                   │                │
                        WS Conn #1 │                │ WS Conn #2
                                   ▼                ▼
                    ┌─────────────────────┐  ┌─────────────────────┐
                    │  WS Gateway Pod #1  │  │  WS Gateway Pod #2  │
                    │  (Holds Alice Conn) │  │  (Holds Bob Conn)   │
                    └──────────┬──────────┘  └──────────┬──────────┘
                               │                        │
                               │ SUBSCRIBE              │ SUBSCRIBE
                               │ "notify:alice"         │ "notify:bob"
                               ▼                        ▼
                    ┌──────────────────────────────────────────────┐
                    │            Redis Pub/Sub Backplane           │
                    └──────────────────────▲───────────────────────┘
                                           │
                                           │ PUBLISH "notify:bob" {title: "Alice liked..."}
                                           │
                            ┌──────────────┴──────────────┐
                            │ Notification Worker Service │
                            └─────────────────────────────┘
```

### 7.1 The Distributed Connection Challenge
In a multi-node Kubernetes deployment:
* User Alice might connect to `WS Gateway Pod #1`.
* User Bob might connect to `WS Gateway Pod #2`.
* When Alice likes Bob's post, the notification processor running on a background worker doesn't know which gateway pod Bob is connected to.

### 7.2 The Redis Pub/Sub Solution
1. **Dynamic Subscription**:
   * When Bob connects to `WS Gateway Pod #2` and completes JWT authentication, Pod #2 issues:
     `SUBSCRIBE notify:<bob_user_id>`
2. **Targeted Publishing**:
   * When the background worker creates a notification for Bob, it simply executes:
     `PUBLISH notify:<bob_user_id> <payload_json>`
3. **Decoupled Delivery**:
   * Redis Pub/Sub instantly routes the message to `WS Gateway Pod #2`.
   * Pod #2 writes the frame to Bob's WebSocket. Pod #1 never sees or processes the message, keeping overhead negligible.
4. **Disconnect Cleanup**:
   * When Bob disconnects, Pod #2 calls `UNSUBSCRIBE notify:<bob_user_id>` and releases the goroutine.

### 7.3 Connection Health & Heartbeats
* **Ping / Pong**: The server sends a WebSocket `Ping` frame every 30 seconds. If a client does not reply with a `Pong` within 60 seconds, the connection is deemed dead and terminated to reclaim file descriptors and memory.
* **Client Reconnect & Sync**: Mobile devices frequently disconnect due to cell tower switches or app backgrounding. Upon reconnecting, the client calls `GetNotifications(since_timestamp)` to catch up on any notifications that occurred while offline.

## 8. External Push & Email Delivery Pipeline


### 8.1 Push Notification Best Practices
1. **BadDeviceToken Handling**: If APNs returns `410 Gone` or FCM returns `UNREGISTERED`, the token is immediately marked `is_active = FALSE` in `user_device_tokens` to prevent sending to dead tokens.
2. **Payload Size Limits**: APNs enforces a 4KB maximum payload. Push payloads only send minimal meta:
   ```json
   {
     "aps": {
       "alert": {
         "title": "SocialFlow",
         "body": "Alice liked your post: 'Hello World!'"
       },
       "badge": 3,
       "sound": "default"
     },
     "data": {
       "notification_id": "c1f727c9-...",
       "action_url": "socialflow://posts/123"
     }
   }
   ```
3. **HTTP/2 Connection Pooling**: The APNs gateway utilizes multiplexed HTTP/2 persistent connections to avoid TLS handshake penalties on every push alert.

## 9. Critical Distributed Systems Challenges & Solutions

### Problem 1: The Celebrity / Viral Post Notification Spike
* **Scenario**: A celebrity with 10M followers publishes a post. Within 1 minute, 100,000 users like the post.
* **Failure Mode**: The notification service receives 100,000 `PostLikedEvent`s within 60 seconds, overwhelming the database and spamming the celebrity's phone with 100,000 pushes.
* **Engineering Solution**:
  1. **Celebrity Mode**: Accounts with $> 100,000$ followers have real-time push notifications disabled by default for likes and follows.
  2. **Sliding-Window Aggregator**: In-memory Redis buffering collapses likes into 5-minute batches before updating PostgreSQL.
  3. **Rate Throttling**: A per-user rate limiter allows at most 1 mobile push notification every 15 minutes for the same post.

### Problem 2: At-Least-Once Delivery & Idempotency
* **Scenario**: The worker processes an event, saves it to PostgreSQL, but network latency causes Redis Streams to redeliver the event before `XAck` completes.
* **Failure Mode**: Duplicate notification rows created, incrementing unread counters twice.
* **Engineering Solution**:
  * An idempotency check uses Redis:
    ```go
    key := fmt.Sprintf("dedup:%s:%s:%s", event.ActorID, event.Type, event.EntityID)
    ok, err := redisClient.SetNX(ctx, key, "1", 60*time.Second).Result()
    if !ok {
        // Duplicate event, skip processing and ACK immediately
        return nil
    }
    ```
  * In PostgreSQL, a unique partial constraint on active unread notifications prevents duplicate unaggregated entries:
    ```sql
    CREATE UNIQUE INDEX uq_unaggregated_like 
    ON notifications (recipient_id, entity_id, type) 
    WHERE is_read = FALSE AND type = 'post_like';
    ```

### Problem 3: The "Un-Action" Problem (Like followed immediately by Unlike)
* **Scenario**: User A accidentally likes a post and clicks "unlike" 1 second later.
* **Engineering Solution**:
  * If the notification hasn't been read:
    * When `PostUnlikedEvent` arrives, decrement the aggregated like count.
    * If `total_actors_count <= 0`, delete or archive the notification row and decrement `unread_count`.
  * If the notification was already pushed:
    * Do not crash or retract native push; simply adjust the in-app state when the user opens their inbox.

### Problem 4: Poison Messages & Consumer Group Recovery
* **Scenario**: A malformed event (missing required fields or containing invalid JSON) crashes the consumer handler.
* **Failure Mode**: The consumer restarts, re-reads the same bad event, and crashes in an infinite loop.
* **Engineering Solution**:
  * Capture decode errors; log and immediately `XAck` unprocessable messages.
  * For database outages, leave the message unacknowledged. The `reclaimPending` worker uses `XAutoClaim` to re-process idle messages after backoff.
  * If a message delivery attempt exceeds 5 attempts, forward it to a Dead Letter Queue (`stream:notifications:dlq`) and acknowledge it in the main stream.
